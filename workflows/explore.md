# 探索与审美校准

用于校准审美，或为新界面探索方案。目标是让用户通过比较说出判断，而不是由 agent 展示一个答案。

## 开始前

1. 确定真实内容和这个界面的主要操作。没有真实内容就先问用户，不要用占位文字做判断。
2. 确定目标平台，读 `platforms/` 里对应的文件。
3. 读 [foundations/taste.md](../foundations/taste.md)：明确偏好要遵守，待验证项是可以比较的内容。
4. 查 `references/` 里有没有相关点评。

## 每轮怎么做

一轮只比较一个维度，从难改的开始：

1. 结构：信息分组、导航位置、主要操作的位置
2. 排版和密度：字号层级、行距、一屏内容量
3. 视觉方向：字体气质、色彩用量、形状语言
4. 动效和细节

每轮给 2–3 个方案。每个方案都要：

- 用同一份真实内容和同样的主要操作。
- 用一句话说明它押注什么、牺牲什么。
- 通过**灰阶测试**：去掉所有颜色后，方案之间仍能一眼区分。做不到就不算不同的方案。专门比较色彩的那一轮除外。

## 跨平台比较

任务要跨平台时，把同一个任务放到差异最大的两三个平台上，各做一个草图，比如桌面宽度的 Web、手机和终端。

- 看信息层级和主要操作是否都还成立。
- 都成立的部分写入推测，作为通用层的候选；只在部分平台成立的部分留在平台层。
- 和用户逐项确认哪些地方必须一致，哪些应该随平台变化（`foundations/taste.md` 的 O-009）。

## 怎么提问

- 每次最多 3 个关键问题，每个问题都附上你的建议。
- 问具体的地方，比如「A 和 B 的列表，哪个扫读更快？」，不要只问「喜欢哪个风格」。
- 用户用形容词时，接着问它指向画面的哪一部分。
- 用户可以拼接。「A 的结构配 B 的字体」是有效答案。

## 怎么记录

每轮结束后马上更新：

- 用户说的话写入 `foundations/taste.md` 的明确偏好，保留原话和适用范围。
- 你的归纳写入推测，并写明证据和验证方式。
- 新出现的问题写入待验证。
- 本轮的方案、选择和落选理由写入 `explorations/YYYY-MM-<主题>/README.md`。

落选不等于禁止。记录的是「在这个情境下没选，因为……」。

## 文件约定

- 路径：`explorations/YYYY-MM-<主题>/`，里面放 `README.md` 和自包含的 HTML 或图片。
- 方案文件放在目录顶层，[查看器](../viewer/README.md)会自动显示，并提供窗口宽度切换和灰阶。
- 能渲染就先渲染，看过截图再给用户。做不到就说明这些方案没有经过渲染检查。
- 只留下对判断有用的截图，注意体积。

## 校准得够不够

用**预测测试**判断。出下一轮方案前，先把预测写下来：用户会选哪个，为什么。给用户看方案时不要透露，选完再对照。

- 连续预测正确，说明记录下来的判断有用。
- 预测错了，差异本身就是新的待验证项。
- 第四阶段让一个全新的会话只靠本库做同样的预测。

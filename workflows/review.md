# 审阅与验证

三项分别检查、分别报告。一项通过不代表其他项通过。

## 1. 功能正确

- 主要操作能完成，结果正确。
- 数据和跳转符合预期。
- 产品有测试的，测试通过。

证据：测试结果或操作记录。

## 2. 视觉一致

必须实际渲染并看过截图。

- **窗口尺寸（Web）**：1440×900、1024×768、390×844，再加上宽度为 `constraint.reflow.width` 的重排检查。
- **对照依据**：已采用的规范、认可的示例和产品 `DESIGN.md`；数值是否来自 tokens。
- **内容压力**：先用真实内容，再用 [content-stress.json](../foundations/content-stress.json) 检查中文、英文、混排、长文本和极端数量。
- **字体**：字体是否真的加载了，中文回退字体是否符合预期。
- **灰阶**：选中、错误等状态在灰阶截图里还能分辨吗（`foundations/baseline.md` 的 BASE-3）。
- **深色模式**：产品支持时单独检查。

证据：截图路径和对应的尺寸。

## 3. 交互可用

- 只用键盘走完主要流程：顺序、焦点可见性、弹层开关后的焦点。
- 逐项走[状态清单](../patterns/README.md)：焦点、选中、禁用、加载、空状态、错误、成功。
- 人为制造问题：放慢网络、让请求失败、清空数据。
- 放大到 200%；打开系统的减少动态设置。
- 能做就用读屏软件走一遍；做不到就列入「未覆盖」。

证据：走过的流程和结果。

## 按平台

| 界面 | 可以先用什么查 | 最终验证 |
|---|---|---|
| Web | 浏览器渲染和截图 | 目标浏览器 |
| 原生 | Web 原型只能验证结构和内容 | 原生运行环境。模拟器可查布局和流程，手感和性能要看真机 |

## 验证记录

写在 `examples/<页面>/README.md` 或回复里。没有做的项目不要删，写「未检查」和原因。

```markdown
## 验证记录

- 日期和版本：2026-11-05，<提交或标签>
- 阶段：草图探索 / 视觉设计 / 交互原型 / 生产实现
- 环境：<浏览器或设备，系统版本>
- 实际检查的尺寸：<例如 1440×900、390×844>
- 功能正确：通过 / 未通过 / 未检查 —— <证据>
- 视觉一致：通过 / 未通过 / 未检查 —— <截图路径>
- 交互可用：通过 / 未通过 / 未检查 —— <走过的流程>
- 未覆盖：<没有检查的内容和原因>
```

没有渲染能力时，视觉一致写「未检查」和原因，不要根据代码推断通过。

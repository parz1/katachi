# 沉淀：按用户的反应修订规范

规范是主动定下来的，这里写怎么修订它。用户认可、否决或改了某个做法时做，可以在产品的会话里当场做，也可以事后补。用户说“沉淀一下”时就是这件事。

1. **找证据。** 用户认可或否决了什么，原话是什么；对应的原型、提交或 artifact 链接。找不到用户的话，就不算认可。

2. **决定写到哪。** 已有页面就改已有的，不新开。

   | 这次得到的 | 写到 |
   |---|---|
   | 跨产品都成立的判断 | `DESIGN.md` 的「定了的」 |
   | 排版、颜色这些基础，或交互的默认做法 | `standards/<名称>.md` |
   | 一类界面或交互的做法 | `patterns/<名称>.md` |
   | 值得照着学的真实界面 | `examples/<产品>-<界面>/` |
   | 数值 | `tokens/katachi.tokens.json` |
   | 只在某个平台成立 | `platforms/<id>.md` |
   | 被否决的做法，原因能帮到下一次 | 对应页面的规则或示例的「别学什么」，写清什么情境下不用 |
   | 从几次反应里猜到的倾向 | `DESIGN.md` 的「有迹象」，写明证据 |
   | 新冒出来、还没答案的问题 | `DESIGN.md` 的「没定的」 |
   | 只属于一个产品 | 产品自己的 `DESIGN.md`，不写到这里 |

3. **写给 agent 看。** 每条都是「做 X 时这样做」，能照着做，也能被检查。原话、日期和来源放进 `notes.md` 或示例的 README，页面里只留规则。删掉这一条 agent 的产出也不会变，就别写，比如“保持一致”。

4. **原料不搬进来。** 产品仓库、claude.ai 和会话记录留在原处，写链接或提交号。只复制学的时候真要打开的东西：截图和能运行的原型。交互只看截图学不到，涉及交互时尽量留能运行的原型。外观是产品自己的选择时，写进「别学什么」。

5. **更新入口。** 新页面加进 `DESIGN.md` 的表格，新示例加进 `examples/README.md`。

6. **检查。** 运行 `node tools/check.mjs`，在查看器里看一眼。

7. **给用户看改动，点头再提交。** 只有用户说过的才能写进「定了的」，agent 的归纳只能写进「有迹象」。

## 批量沉淀

从一个范围里找候选时（比如一个产品最近的提交，或 claude.ai 上的一批原型），步骤一样，只是第 1 步先列清单：每条写清是什么、证据在哪、建议写到哪。用户挑过之后再动手。每次不超过 3 件需要用户判断的事。

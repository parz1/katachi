# katachi

我的 UI 设计资产库，名字取自日语「形」（かたち）。这里沉淀审美判断、设计规范、tokens、界面模式、参考和正式素材，供我本人、Claude 和 Codex 在多个产品项目中使用。范围是全平台：Web、桌面、手机、折叠屏与自适应、终端、POS 等。

它不是组件库，也不是一套现成的风格。这里的每条审美规则，都要能追溯到我对具体方案的真实反应。

> **当前状态：0.0.x 骨架，第一阶段已完成。** 审美还没有校准，现在不能用它决定任何产品的视觉。

## 结构

每个平台分别处理，在这之上放通用的东西。

| 层次 | 内容 | 位置 |
|---|---|---|
| 通用层 | 审美判断、原则、语义角色、交互状态、内容规则、可访问性目标 | [foundations/](foundations/README.md)、[tokens/](tokens/README.md)、[patterns/](patterns/README.md) 的通用部分 |
| 平台层 | 每个平台的能力、要求、检查项，以后还有语义映射和专属模式 | [platforms/](platforms/README.md) |
| 产品规范 | 每个产品选择自己的布局、密度、组件和平台行为 | 产品仓库的 `DESIGN.md` |
| 技术实现 | 各平台可以不同 | 产品仓库 |
| 参考 | 用来学习判断，不能直接进入产品 | [references/](references/README.md) |
| 正式素材 | 自有或获准使用，登记来源和授权 | [assets/](assets/README.md) |

通用规则从平台中提炼：在两类差异大的平台上都成立，才算通用，并标明它在每个平台上的应用面。见[决策 0004](decisions/0004-platform-layering.md)。

流程在 [workflows/](workflows/README.md)，重要取舍在 [decisions/](decisions/README.md)。`explorations/` 和 `examples/` 等到有第一份真实内容时才创建。

## 怎么用

- **我本人**：用真实界面和方案比较推动它成长。随时查看并修正[审美账本](foundations/taste.md)，里面写错的，以我说的为准。
- **AI agent**：从 [AGENTS.md](AGENTS.md) 或 [CLAUDE.md](CLAUDE.md) 进入，再由 [AGENT_GUIDE.md](AGENT_GUIDE.md) 按任务指向该读的文件。
- **产品项目**：锁定一个版本，把自己的规范和例外写进产品仓库的 `DESIGN.md`。见[接入说明](workflows/adopt.md)。

### 最小可用版本（v0.1.0）

**包含**：通过真实比较得到的审美账本；一个代表性界面和一个在另一类平台上的复用验证界面，都带验证记录；这两个界面实际用到的 tokens 和模式；探索、实现、审阅三份提示词；一份产品接入示例。

**不包含**：
- 所有平台都做到位。全平台是长期范围，v0.1.0 只验证差异大的两类，其他平台等有真实产品时再接入。
- 组件库、npm 包、发布流水线、多框架适配、文档网站、设计工具同步。
- 没有在真实界面出现过的模式。
- 各平台的 token 生成器，第一个项目接入时再加。

## 维护

改完就运行：

```bash
node scripts/check.mjs
```

它检查 tokens 是否有效、生成物是否过期，文档里的 token 名和链接是否存在，账本条目是否带证据，平台文件和基线表格是否一致，参考和素材是否登记来源与授权等。只需要 Node，没有其他依赖。改了校验脚本本身，再运行 `node scripts/check.test.mjs`，确认每条规则真的会报错。

发布版本时：更新 [CHANGELOG.md](CHANGELOG.md)，校验通过后打标签（`git tag -a vX.Y.Z`）。版本号规则见[接入说明](workflows/adopt.md)。

仓库默认私有：`references/` 可能包含版权属于他人的截图，公开前要先处理。

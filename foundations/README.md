# 基础（通用层）

所有平台和产品共享的判断和规范。各平台的具体做法在 [platforms/](../platforms/README.md)。

## 通用层和平台层怎么分

下面是初始划分，要由真实界面检验（见 `taste.md` 的 O-009）。

| 领域 | 通用层放什么 | 平台层放什么 | 状态 |
|---|---|---|---|
| 审美判断 | [taste.md](taste.md) | — | 进行中，未做过视觉比较 |
| 设计原则 | 全部 | — | 待校准 |
| 文字 | 层级的角色、混排规则 | 具体字体和字号 | 待校准 |
| 颜色 | 语义角色 | 颜色值或终端色 | 待校准 |
| 间距 | 分组关系和比例 | px、pt、dp 或字符单元 | 待校准 |
| 密度 | 判断方法 | 每个平台的舒适范围 | 待校准 |
| 动效 | 意图和减少动态的要求 | 时长、曲线和实现 | 待校准 |
| 可访问性 | 目标：[baseline.md](baseline.md) | 做法和数值 | 已写，未经真实界面检验 |
| 交互状态 | [状态清单](../patterns/README.md) | 具体表现和额外状态 | 已写，未经真实界面检验 |
| 内容 | [内容压力测试集](content-stress.json) | 平台的额外情况 | 已写，未经真实界面检验 |

待校准的领域现在没有文件。这是有意的：文件等有依据时才创建。

## 规则怎么进入通用层

1. 新规则先写在平台文件或产品规范里。
2. 在两类差异大的平台上都成立，才提到通用层，并标明应用面。
3. 拿不准时做**最窄平台测试**：把规则放到终端上试一下。离不开像素、字体、圆角或阴影的，属于平台层；能用层级、角色和状态说清楚的，才可能属于通用层。

通用基线是例外：它来自外部标准，一开始就放在通用层。

用户可以决定提前把规则放进通用层。这时状态写 draft，应用面如实写，没验证过的平台不能写「已验证」。

## 规则格式

重要规则尽量包含下面每一项。缺示例就写明「待补」，不要省略。

```markdown
### <编号> <一句话规则>

- 状态：standard / draft / adopted / validated
- 适用：什么情境下用；什么情境下不用
- 做法：具体数值或行为（数值写 token 名，不复制数值）
- 示例：链接到 examples/ 或截图
- 理由：为什么这样做
- 例外：什么时候可以不遵守
- 依据：taste.md 条目，或标准条款
- 应用面：每个目标平台写 已验证、已映射、不适用 或 未做
```

## 规则状态

| 状态 | 条件 |
|---|---|
| standard | 来自外部标准或平台规范，不是审美选择 |
| draft | 在一次探索或页面中用过，还没得到用户认可 |
| adopted | 用户认可，并用在至少 1 个认可的示例里 |
| validated | 在第二类平台或第二个产品中复用，没有修改，或修改后又验证过 |

## 应用面

应用面说的是规则在某个平台上的情况，规则状态说的是整条规则。

| 标记 | 含义 |
|---|---|
| 已验证 | 在这个平台的真实界面上用过，并在它的运行环境里检查过 |
| 已映射 | 写清了在这个平台上的做法，还没有真实界面 |
| 不适用 | 这个平台没有对应的问题，并写明原因 |
| 未做 | 还没考虑 |

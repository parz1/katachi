# 0004 全平台：每个平台分别处理，通用层从中提炼

- 状态：结构采用；「两类平台」门槛和最窄平台测试试行
- 日期：2026-11-05

## 背景

用户要做全平台设计：Web、桌面、手机、折叠响应式、终端、POS 等（`foundations/taste.md` 的 S-009），并提出每个平台分别处理，在这之上放通用的东西（S-010）。这些平台的差别不只是尺寸：终端没有像素和固定配色，字体也由用户决定；POS 的约束来自硬件和收银场景。

## 决定

- `platforms/<id>.md`：每个平台一个文件，写能力、平台要求、必查项和验证环境。新增平台只需要加文件和表格列。
- `foundations/` 和 `patterns/` 的通用部分只放平台无关的意图和语义。数值和外观放平台层。
- 通用规则从平台中提炼：在两类差异大的平台上都成立，才提到通用层。拿不准时做最窄平台测试。外部标准的基线是例外。
- 应用面要能查到：通用基线和界面模式都按平台标注。校验脚本检查表格和平台文件是否一致。
- 平台文件现在只写事实和检查项，不写视觉规范。有真实产品时才增加语义映射和平台专属模式。
- tokens 用 `platforms` 字段标明适用平台，Web CSS 只输出适用于 Web 的 token。
- v0.1.0 不覆盖所有平台，只验证响应式 Web（含手机和折叠屏宽度）和终端（S-012）。第一个界面放在响应式 Web，复用验证放在终端：终端的约束最多，最能检验哪些规则真的通用。
- POS 这类由特定硬件和业务流程决定的特殊场景暂缓（S-011）。已查到的资料留在 `platforms/later/`，不算当前平台。

## 备选和放弃原因

- **一套视觉规范用于所有平台**：在终端和 POS 上不成立。
- **先把 Web 做完再移植**：像素、悬停这些假设会混进基础，要到移植时才发现。
- **立刻给每个平台做完整的子系统**：没有真实产品验证，维护量成倍增加，违背轻量的目标。
- **所有平台写在一个文件里**：agent 要读不相关的内容，新增平台也不够清楚。

## 代价

- 每条通用规则都要标应用面，写规则更慢。
- 平台多了容易变成几套互不相干的设计系统，要靠语义层和应用面表格防止。
- 部分平台的最终验证依赖实机或特定环境，短期内可能一直是「未检查」。
- 决策 0002 里「需要第二个输出目标时重新评估」会提前到来。
- 平台值的存放方式还没定。终端颜色无法用 DTCG 的 color 类型表达：它需要 `colorSpace` 和 `components`，而终端的 16 色由用户主题决定。第一次需要时再决定。

## 什么时候重新考虑

两类以上平台有真实界面后，检查通用层有没有实际内容。如果通用层一直很空，或者平台之间经常冲突，就重新划分。
